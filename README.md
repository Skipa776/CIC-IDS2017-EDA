# Can a network intrusion detector catch attacks it has never seen?

Trained on earlier capture days and tested on later ones, mostly no. On CIC-IDS2017 and
CSE-CIC-IDS2018, the strong results trace to artifacts or single-feature shortcuts. The one clean
success is recognizing a known attack on a later date. Random train/test splits hide all of this
by scoring near 1.0.

## Headline: train on earlier days, test on later days

Each row trains on capture days before the test day, freezes its alert threshold on validation
benign traffic at a 1% budget, then scores the test day once. Five seeds per row. A recall is shown
only if the actual test false positive rate stayed within 1.5 times the budget.

**What this shows.**

- **Unseen attack families are rarely caught for the right reason.** The best 2017 result rides on
  one victim server's TCP window value ([03_forward_2017](notebooks/03_forward_2017.ipynb)), and
  2018's new family (Bot) is caught by nothing.
- **A known attack on a later date can be caught.** The 2018 web attacks return the next day and
  LightGBM catches most of them with no shortcut flag. New tools in a known family are caught too,
  but one feature alone does as well as the model.
- **Thresholds drift.** A threshold frozen on earlier days often lets through far more than 1% of
  a new day's benign traffic. Anomaly models (Isolation Forest, autoencoder) drift the most, which
  is also why combining them with a supervised model did not help
  ([05_high_recall_hybrid](notebooks/05_high_recall_hybrid.ipynb)).

## Sanity check: why random splits score near 1.0

A random split puts flows from the same capture in train and test. LightGBM then scores average
precision 0.9998. It stays at 0.9908-0.9997 when similar flows are kept on one side of the split,
or when the test is the end of each capture file. When the test is a new day, it falls to 0.22-0.79 ([02](notebooks/02_why_random_splits_mislead.ipynb),
`reports/leakage_audit.json`). Leakage was checked and is minor: few exact input twins, a
shuffled-label control at chance. The near-perfect score is real but answers an easy question:
"does the model recognize this capture's attacks?"

## What the data looks like

- **Most "web attack" rows are not attacks.** 628 of 652 XSS flows and 1,356 of 1,507 web
  brute-force flows carry no payload in either direction: three packets out, one back, answered
  by the victim server. This is consistent with the "TCP appendix" defect reported for this dataset
  ([01c](notebooks/01c_eda_data_quality.ipynb)).
- **71 features, far fewer signals.** Four column pairs are identical in every flow (including a
  SYN-flag count equal to the forward PSH-flag count, a flow-tool defect), and at rank correlation
  0.95 the features fall into 42 groups ([01b](notebooks/01b_eda_features.ipynb)).
- **Port and protocol give attacks away in the lab.** Each attack family uses one service (all DoS,
  DDoS and web attacks on port 80) and every attack completes a TCP handshake, against 56% of
  benign flows ([01a](notebooks/01a_eda_overview.ipynb)).
- **Labels conflict and rows repeat.** 697 distinct flows carry contradictory labels, and nearly
  half of SSH-Patator and PortScan rows are exact repeats.

## Data and cleaning

- A first cleaning pass treated `Init_Win_bytes = -1` ("no TCP window observed") as corrupt and
  kept 1,388,089 of 2,830,743 rows. The fix keeps those 1,439,672 flows with indicator columns.
- Evaluation uses a copy that keeps repeated flows and conflicting labels (2,827,726 rows), since
  real traffic has both and removing conflicts dataset-wide uses test labels before the split.
- CSE-CIC-IDS2018's 78 columns map one to one onto 2017's. Benign flows are a 10% sample, weighted
  back in prevalence-dependent metrics.
- The flow tool changed between the datasets. Single-packet DNS queries record an 8-byte forward
  header in 2018 and 20-40 bytes in 2017 ([06_cross_year](notebooks/06_cross_year.ipynb)).

## Limits

- Lab-generated traffic from one institute and one flow tool; known label errors
  (Engelen, Rimmer & Joosen, 2021).
- In 2017 each attack family occurs on one day, so "new day" and "new attack" cannot be separated.
- Seed ranges measure fitting variation, not uncertainty about future traffic.
- Every capture here has been examined before; these are development results, not a fresh test.
- Flow features cannot see payloads.

## Reproduce

```sh
conda env create -f environment.yml && conda activate cicids-eda
# CIC-IDS2017 MachineLearningCVE CSVs -> cic-ids-eda/data/raw/MachineLearningCVE/
# CSE-CIC-IDS2018 "Processed Traffic Data for ML Algorithms" (public S3 bucket cse-cic-ids2018)
#   -> data/raw/CSE-CIC-IDS2018/
python scripts/build_dataset.py --year 2017 --no-dedup
python scripts/build_dataset.py --year 2018 --no-dedup
python scripts/run_pipeline.py             # every detector, fold and seed -> reports/results/
python scripts/summarize_results.py        # -> reports/results/summary.json
python scripts/explain_forward_thursday.py # the fold B explanation
python scripts/build_readme_tables.py      # results tables above
python scripts/build_notebooks.py && jupyter nbconvert --to notebook --execute --inplace notebooks/0*.ipynb
pytest tests/
```

`scripts/check_reproduction.py` confirms the evaluation code reproduces an independent earlier
evaluation exactly. `scripts/audit_leakage.py` reruns the same-capture leakage audit.

## Other components

`api/` serves the original two-layer LightGBM model with MITRE ATT&CK mapping
(`api/services/mitre_mapping.py`); `tests/` covers it. That model uses 20 features chosen on all
data before a split and is **not validated on unseen attacks** (see `models/MODEL_CARD.txt`).
`reports/soc_triage_playbook.md` describes how an analyst should read its alerts.
